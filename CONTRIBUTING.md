# Изменения и коммиты

До работы проверь `git status --short`. Сохраняй существующие изменения пользователя. Делай отдельный коммит на каждый законченный логический шаг; крупный milestone разбивай на проверяемые шаги.

Формат сообщения: `type(scope): concrete change`. Типы: `feat`, `fix`, `docs`, `chore`, `test`, `refactor`, `build`, `ci`. Это установленное здесь правило: раньше в истории был только `init`, отдельной конвенции не было.

Перед коммитом:

1. Обнови `docs/STATUS.md`: что сделано, команды и результаты проверок, реальные ограничения, следующий шаг. Обнови карту и решения, если они изменились.
2. Запусти `scripts/check-workspace.ps1`, `git diff --check` и проверки, относящиеся к изменению. Для кода приложения обязательны сборка, релевантные тесты и lint.
3. Добавь только перечисленные относящиеся к шагу файлы через `git add -- <paths>`. Проверь `git diff --cached --stat` и `git diff --cached --check`, просмотри содержимое staged diff.
4. Сделай коммит. Проверь `git log -1 --oneline` и `git status --short`.

Не коммить `.toolchain/`, `local.properties`, keystore, токены, экспорты пользователей и реальные чувствительные данные. Не использовать `git add .`, amend/rebase/reset существующих коммитов как рутинный способ сохранения. Push и публикация выполняются отдельным явно запрошенным действием.

STATUS описывает состояние, включённое в коммит. SHA последнего коммита получает `resume.ps1` из Git — записывать SHA коммита внутри него самого не нужно.
