Прежняя подготовительная схема этапа 1:

На этапе 1 введена Room v7, [7.json](../app/schemas/app.ritela.data.RitelaDatabase/7.json). Явная MIGRATION_6_7 добавляет только `sync_profile_state`, `sync_authority`, `sync_record_versions`, `sync_links`; определения и значения прежних шести таблиц сохраняются. Миграции 1→6 и их schema JSON не менялись. Имена профильных баз, файлы ключей/дудлов/DataStore, backup и wire format прежние.

`sync_profile_state` — singleton id=1, internetEnabled INTEGER 0/1, default 0. `sync_authority` — singleton id=1 с generation/lastSequence=0, state=UNINITIALIZED и NULL ссылками на owner/author/grants. `sync_record_versions` (PK ownerIdentity/entityType/entityKey) и `sync_links` (PK peerIdentity/peerDevice) после миграции пусты. Точное описание столбцов и defaults — [этап 1 Sync](architecture/RITELA_SYNC_STAGE_1.md). У fresh Room 7 singleton defaults вставляются идемпотентно первым вызовом локального SyncStateStore; отсутствие строки до этого равно off/uninitialized. Этот reader не подключён к старым edit/send paths.

Флаги Room entity хранятся как Int, чтобы значение вне 0/1 не становилось Boolean true. Store валидирует metadata и возвращает типизированный отказ для повреждённых/неизвестных значений, несогласованных scopes и любого авторства без будущей криптографической проверки. У него нет методов opt-in/activate/transfer. Миграция не читает vault и не создаёт ключи/grants, revisions не выводятся из updatedAt. Существующие теги не получают Sync-допуск. Для будущих tag record keys используется `sectionId/tagId`, чтобы одинаковые tag ID в разных разделах не конфликтовали.

Этап 1 добавляет только локальное неактивное хранение: INTERNET/ACCESS_NETWORK_STATE и сетевых зависимостей нет, queue/journal/backfill/relay/автоматический Bluetooth не добавлены. Доменные интернет-лимиты отдельно от legacy Doodle/PartnerCodec, сохранённые большие рисунки остаются читаемыми.

Предыдущая схема — Room v6, [6.json](../app/schemas/app.ritela.data.RitelaDatabase/6.json). MIGRATION_5_6 добавляет в partner_messages hiddenFromChat INTEGER NOT NULL DEFAULT 0. Миграция сохраняет все прежние поля и таблицы. Скрытый полученный DATA может сохранять body/envelope для главной и календаря; удалённое содержимое заменяется пустыми строками с сохранением ID, личности, устройства и типа. Повторный импорт не восстанавливает строку чата; ACK/OPENED обновляют только hiddenFromChat=0. Обычный backup и wire format прежние.

Уточнение 2026-10-11: для новых стандартных тегов и JSON без withoutPenetration значение true по умолчанию имеют MASTURBATION и ORAL. Сохранённые явные true/false остаются прежними. В интерфейсе свойство называется «Без проникновения / Без партнёра»; SQL-схема, ID тегов и записи дней не меняются.

Room database v4: исходный пользователь хранит `ritela.db`, остальные — `ritela-<UUID>.db`; схема [4.json](../app/schemas/app.ritela.data.RitelaDatabase/4.json); исходная [v1](../app/schemas/app.ritela.data.RitelaDatabase/1.json) сохранена для migration. Таблица `periods`:

| Поле | Формат |
|---|---|
| id | UUID, TEXT primary key |
| startDay | LocalDate.toEpochDay(), INTEGER, unique index |
| endDay | Epoch day или NULL для продолжающегося периода |
| createdAt | Instant epoch milliseconds |
| updatedAt | Instant epoch milliseconds |

Calendar date не переводится в UTC timestamp. Только адаптер Material DatePicker использует UTC midnight, как требует API picker; результат сразу преобразуется в LocalDate/epoch day.

Правила: начало/окончание не позже текущего локального дня; окончание не раньше начала; один день включительно допустим. Записи не пересекаются, включая граничный день. Открытый период занимает интервал до его явного завершения. Проверка пересечения и вставка атомарны; завершение обновляет только ещё открытый период и сохраняет UUID/createdAt.

Редактирование проверяет пересечения, исключая собственную запись, и обновляет даты внутри транзакции. UUID/createdAt сохраняются; updatedAt обновляется. Неудачная правка не меняет данные. Удаление — отдельная операция по UUID; UI требует подтверждение. Повторная операция над отсутствующим UUID возвращает ошибку и не создаёт запись. Завершение дополнительно проверяет startDay <= endDay в SQL для защиты от конкурентной смены начала.

DAO/Repository читают все записи: это нужно календарю и расчёту цикла. История доступна в календаре целиком; на главной графики. Производные прогнозы вычисляются заново и не сохраняются в таблице. Реализован зашифрованный JSON backup и merge: [BACKUP.md](BACKUP.md). Схема v2 добавляет day_logs; явная MIGRATION_1_2 не меняет periods. Для последующих изменений схемы обязательна явная migration с автоматической проверкой.

Реестр пользователей хранится в приватных SharedPreferences `users` одним JSON `catalog`: active UUID и список id/name. Первый UUID фиксирован, имя по умолчанию `qwerty`; имя можно менять без изменения пути базы. Имена после trim должны быть непустыми, уникальными без учёта регистра, до 80 символов. Реестр сохраняется синхронно, выбор последнего пользователя восстанавливается при запуске. Профили не требуют аккаунта и не являются защитой доступа между людьми с доступом к телефону. Любой профиль можно удалить с подтверждением: если он активен, выбирается оставшийся, а при удалении последнего создаётся пустой `qwerty` с новым UUID. Удаляется только соответствующая база и её SQLite sidecars; после удаления исходного профиля очищаются legacy preferences `settings`. Удаление сначала атомарно фиксируется в каталоге (`deleted`: очередь UUID), затем закрывается сессия и очищаются файлы; незавершённая очистка повторяется при старте. Удалённые UUID не используются повторно. `nameVersion=1` отмечает однократный перевод исходного имени «Я» в `qwerty`; пользовательские имена сохраняются, при конфликте используется свободный суффикс.

Версия 4: MIGRATION_3_4 добавляет `profile_settings(id INTEGER PRIMARY KEY, language TEXT NOT NULL, theme TEXT NOT NULL)`; единственная строка id=1. Язык: system/ru/en, тема: SYSTEM/LIGHT/DARK. SettingsRepository один раз заполняет отсутствующую строку; у первого профиля сохраняет прежнюю тему и поддерживаемый системный per-app язык, у новых — system/SYSTEM. Старые SharedPreferences `settings` остаются на месте, но cycleLength/forecastPeriodDuration не используются: расчёт стартует с 28 дней цикла и 5 дней месячных и уточняется историей.

ProfileSession содержит Room/репозитории и собственный ViewModelStore. Переключение сначала открывает и проверяет новую базу, затем атомарно обновляет выбранный UUID, сбрасывает UI и закрывает старую сессию. Ошибка открытия не переключает профиль. Активное сохранение или backup блокирует переключение. Не используются destructive migrations, старый файл не копируется и не перемещается. Импорт записей, настроек и структуры выполняется в одной транзакции текущей базы. Производные прогнозы не хранятся и вычисляются отдельно для каждого пользователя. Системный backup запрещён.

Таблица day_logs (v2): day INTEGER PRIMARY KEY (epoch day), nullable TEXT headache/cramps/backache/flow/mood/energy с enum names, sex TEXT (имена в алфавитном порядке через запятую), note TEXT (≤1000 символов). Боль NONE/MILD/MODERATE/SEVERE; flow NONE/LIGHT/MEDIUM/HEAVY; mood CALM/HAPPY/LOW/ANXIOUS/IRRITABLE; energy LOW/NORMAL/HIGH. Sex NONE/CONDOM/NO_BARRIER/VAGINAL/ORAL/ANAL/MASTURBATION/OTHER: несколько тегов за день, NONE отдельно от остальных. NULL/пустой набор — не отмечено; NONE — явное отсутствие. Пустая отметка удаляется, сохранение — Upsert по дню. Будущие дни запрещены. Форма draft переживает пересоздание Activity; ошибочное сохранение не закрывает форму.

Версия 3: MIGRATION_2_3 добавляет `day_logs.custom TEXT NOT NULL DEFAULT '{}'` (JSON section ID → tag ID array), nullable `calendarIcon TEXT`, таблицу `journal_layout(id INTEGER PRIMARY KEY, config TEXT NOT NULL)`. Единственная строка id=1; отсутствие строки даёт стандартные разделы. Layout хранит заголовок, разделы с постоянными ID, названиями, иконками, tags и multiple. Допустимы 0..64 раздела, 1..64 тега в разделе; строки до 200 символов, ID до 80. Новые ID — UUID; встроенные остаются именами полей/enum. Изменение структуры не удаляет исторические значения. Произвольный тег не интерпретируется как медицинский enum. Пустые/недопустимые структуры отклоняются.

## Partner / Room v5

Migration 4→5 только добавляет partner_directory (каталог/индивидуальные grants JSON) и partner_messages (UUID primary key, identity/device, direction, kind, timestamps, plaintext local body, encrypted wire envelope, confirmed delivered/opened). Собственные таблицы не меняются. Обычный backup остаётся v3 и не содержит ключей/контактов/полученных snapshots. Отдельные форматы обмена и защищённой личности описаны в [PARTNER](PARTNER.md). Per-user partner preferences в DataStore; перенос устройства требует повторной проверки, merge/group не дают дополнительных grants. Очистка received оставляет ID tombstones.

## 2026-10-11: история тегов

Room остаётся v5: изменения используют прежние JSON поля, без изменения SQL-схемы. В `journal_layout.config` добавлены необязательные `archivedSections` (до 256 разделов/256 тегов в каждом) и `tags[].withoutPenetration` (Boolean; при отсутствии true только для MASTURBATION). Активные разделы/теги сохраняют прежние лимиты 64. Архив хранит названия и свойства удалённых тегов/разделов; обычное сохранение, восстановление defaults и импорт структуры объединяют его с прежней структурой и не обновляют `day_logs`. Архив переносится обычным экспортом структуры; Partner отправляет названия только в рамках выбранных категорий/тегов.

Несколько настроений: одно встроенное значение остаётся в прежнем `mood`, остальные значения и пользовательские теги — в `custom["mood"]`; чтение объединяет их, редактирование другого поля сохраняет полный набор. Sex.CONDOM/NO_BARRIER сохраняют ID, подписи теперь «Секс с защитой»/«Секс без защиты». NONE совместим с дополнительными тегами; взаимное исключение NONE/CONDOM/NO_BARRIER применяется к новым действиям выбора, а старые сочетания не отклоняются при чтении/импорте. VAGINAL и discharge.UNUSUAL доступны для исторического декодирования, но исключены из нового выбора. Уже потерянное до этого изменения название пользовательского UUID нельзя восстановить из ID: UI показывает «Удалённый тег», не выдаёт UUID за название.
